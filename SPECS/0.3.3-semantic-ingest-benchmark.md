# Karpathy Wiki 0.3.3: source-based multi-object ingest benchmark

## 1. User-approved direction

These decisions are fixed for the next work session:

1. The product model is **source -> knowledge objects -> wiki pages**, not
   source -> one page.
2. One source may produce or update several durable objects: entity, concept,
   query, idea, project, source-note/raw-only record, or a control-plane action
   such as a schema proposal.
3. The ingester should keep model judgment. Do not implement a rigid
   deterministic semantic classifier.
4. Build a benchmark from raw sources and evaluate the resulting temporary wiki
   against expected knowledge objects.
5. Freeze and baseline the current ingester before changing
   `skills/karpathy-wiki-ingest/SKILL.md`.
6. Then improve the ingester instructions so models have clearer orientation
   for multi-object ingest and do not use `concepts/` as the default dumping
   ground.
7. The benchmark should be hard enough to differentiate skill and model
   improvements. It should not be trivial to score 100%.
8. Do not bulk-move existing wiki pages until the instruction contract and
   benchmark shape are approved.

## 2. Problem

A read-only audit across seven local wikis found that category collapse into
`concepts/` is real but not universal. Many pages are mechanically valid
because `type:` matches the directory, required frontmatter exists, and indexes
build, but the semantic filing is often wrong.

Observed patterns:

- named products, tools, services, APIs, repos, components, and people are
  often filed as `concepts/` instead of `entities/`;
- bounded answers, dated audits, readiness checks, comparisons, and operational
  Q&A are often filed as `concepts/` instead of `queries/`;
- future work embedded in a broader page often remains inside a concept instead
  of becoming an `ideas/` page with `status` and `priority`;
- project workstreams with phases, deliverables, go/no-go gates, and pickup cues
  may remain in `concepts/` even when `projects/` exists;
- thin, one-source, promotional, empty-transcript, or low-evidence material may
  become canonical concepts when it should remain raw, become a source note, or
  require more detail.

The current ingester instruction technically supports multiple target pages,
but it does not explicitly require an object inventory before choosing pages.
This encourages the model to pick one broad, safe destination. `concepts/`
becomes the common denominator.

## 4. Skill design

### 4.1 Lead principle

Add a first-class principle near the target-page decision section:

```text
Canonical wiki pages are knowledge objects, not source summaries. A source can
produce zero, one, or several durable objects. Extract objects before choosing
target pages.
```

### 4.2 Object inventory

Before deciding target pages, the ingester must make an explicit internal
inventory. This inventory does not need to be persisted, but the model must use
it before writing.

Each candidate object should have:

- `name`;
- `kind hypothesis`;
- source evidence;
- whether a matching page already exists;
- intended realization: `page`, `update`, `section`, `hold`, `drop`, or
  `propose_schema`.

The inventory is a decision aid, not a rigid classifier.

### 4.3 Category orientation

The skill should give category tests rather than a closed if-then taxonomy:

- `entities/`: named and durable things such as tools, services, APIs, people,
  products, repos, and components. On ties, named software/services/APIs/people
  bias toward entity over concept.
- `concepts/`: reusable mechanisms, principles, models, and patterns. A useful
  counterfactual: if the named product disappeared, would the page still be a
  true reusable idea?
- `queries/`: durable answers, audits, comparisons, readiness checks, or
  operational Q&A that future agents would ask again.
- `ideas/`: future proposed work, experiments, product ideas, or follow-ups.
  Idea pages require `status` and `priority`.
- `projects/`: workstreams with phases, deliverables, go/no-go gates, pickup
  cues, or implementation scope, when the category exists or is explicitly
  approved.
- `source-notes/`, raw-only, or hold: thin, one-source, promotional,
  empty-transcript, low-evidence, or non-canonical material.

### 4.4 Split versus attach

Add guidance that avoids both under-splitting and overproduction:

- Distinct required object kinds should get distinct realizations.
- A reusable lesson about an entity may become an optional concept or a short
  section on the entity.
- If a candidate object cannot be named in a few words without using "and", it
  may be fused from multiple objects.
- If the secondary object is only a short note and fails the counterfactual
  concept test, attach it instead of creating a sibling overview page.
- Most sources should produce 1-2 objects; 0 is valid for low-evidence sources;
  more than 3 should be rare and each object must justify itself.

### 4.5 Anti-patterns

The skill should explicitly warn against dump shapes:

- `concepts/<tool>-overview.md` that restates an entity profile;
- dated audit or comparison filed as `concepts/<topic>-notes.md`;
- broad page that mixes entity, concept, Q&A, and future work;
- blindly following `suggested_pages: concepts/...` when the body clearly
  contains entity/query/idea/project objects;
- creating canonical concepts from empty transcripts, promo lists, or thin
  one-source claims.

### 4.6 Ambiguity

When evidence is ambiguous, the model should preserve evidence and avoid
canonizing too much:

- do not use `concepts/` as the fallback;
- do not use `source-notes/` as a new dumping ground for named durable entities;
- use hold/raw/source-note/needs-more-detail when evidence is too thin;
- propose schema only as a control-plane action, not as a knowledge object;
- update existing pages when the object already exists.

The first scaffold can be non-executable if needed, but it must be precise
enough that a runner can be implemented directly from it.

### 5.2 Fixture case

Each fixture is a case, not just a file:

- `source.md`: frozen raw source text;
- `context.yaml`: capture metadata such as title, suggested pages, capture kind,
  and optional setup flags;
- `wiki_seed/`: optional seeded wiki state for update/merge cases;
- `expected.yaml`: expected knowledge objects and constraints.

Keep source bytes stable. If a source changes, create a new case id instead of
silently rewriting the fixture.

### 5.3 Expected-object spec

Expected specs describe objects, not exact pages:

```yaml
case_id: 0005-multi-object
objects:
  - id: revenue-cockpit
    kind: entity
    presence: required
    category:
      required: entities
      forbidden: [concepts]
    realization: page_or_update
    match:
      names: ["Revenue Cockpit"]
      identifiers: ["revenue-cockpit"]
    claims:
      must:
        - "named internal product"
        - "data contracts"
        - "UI/API behavior"
      must_not:
        - "claim not supported by the source"

  - id: revenue-cockpit-dump
    kind: concept
    presence: forbidden
    reason: "entity + query + idea collapsed into broad concept"
```

Use `required`, `optional`, and `forbidden` objects. This prevents both
all-concepts collapse and overproduction.

### 5.4 Matching protocol

The benchmark needs explicit matching rules:

1. Collect generated/updated pages and structured hold/issue outcomes.
2. Match expected objects by kind plus alias/title/frontmatter overlap.
3. Score claim coverage from source-grounded `must` and `must_not` claims.
4. If an expected object's claims appear inside the wrong broad page, mark it as
   `absorbed` / under-split, not full recall.
5. Extra pages with no unique claims count toward over-split or overproduction.
6. Do not require exact slugs in v1 except for a few sanity fixtures.

### 5.5 Gates and metrics

Gates are deterministic and must pass:

- generated output validates;
- `type` matches first path component;
- indexes build;
- every generated/updated page cites the source;
- manifest `referenced_by` includes every touched page;
- `ideas/` pages include `status` and `priority`;
- no new category is created unless expected or proposed.

Primary MVP metrics:

1. required-object recall by kind;
2. forbidden-concept / dump rate;
3. named-thing-in-concepts rate;
4. under-split rate on multi-object cases;
5. faithfulness violations;
6. low-evidence hold quality.

Do not average these into one opaque score in v1.

### 5.6 Source-material policy

The first MVP fixtures are synthetic and public-safe. Grok 4.6 xhigh was used
as a draft generator for fictional fixture sources, then the fixtures were
normalized into the repository format.

Existing local `wiki/raw` files may be used later only as structural donor
material. They must be copied, sanitized, and usually rewritten before becoming
fixtures. Never symlink live raw files into the benchmark. Never derive
`expected.yaml` from existing wiki pages, because those pages are contaminated
by the current ingester behavior.

Exclude private account data, campaign data, ASINs, spend, health details,
legal or family material, private handles, private vendor quotes, images of
people, and company-identifying paths from committed fixtures.

## 6. MVP scope

The MVP benchmark should focus on the observed failure: concept dumping.

Include:

- obvious entity;
- obvious concept;
- obvious query;
- obvious idea;
- bounded project with `projects/` seeded in the fixture;
- multi-object source;
- adversarial `suggested_pages: concepts/...`;
- low-evidence source that should not create a canonical concept;
- seeded update case where an entity exists and a wrong concept page is a merge
  magnet.
- faithfulness trap where the title invites unsupported platform claims.

Defer:

- provider leaderboard;
- broad custom-category invention;
- heavy stale/conflict handling;
- cross-linking as a scored dimension;
- LLM judge as a required dependency;
- full migration of live wiki pages.

## 7. Challenge benchmark

After MVP is stable, add a smaller, harder challenge set:

- seeded merge magnets;
- multiple queued sources describing the same object with different names;
- stale claims and contradictions;
- category missing but several sources justify a schema proposal;
- mixed sources with several valid decompositions;
- adversarial titles that look conceptual while the body is an entity profile;
- cross-wiki category variation.

The challenge set should be difficult enough that current and future models do
not trivially score 100%.

## 9. Stop rules

Stop and ask before:

- moving live wiki pages;
- changing scheduler/runtime behavior;
- changing provider adapters;
- adding a hard deterministic semantic classifier;
- adding a mandatory LLM judge dependency;
- publishing or pushing if the remote effect is not understood;
- expanding the work into a broad taxonomy redesign.
