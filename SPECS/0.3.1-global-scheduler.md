# Karpathy Wiki 0.3.1: one machine-wide scheduler

## 1. User-approved decisions

These constraints are fixed for this release:

1. Install exactly one scheduler per machine, not one LaunchAgent per wiki.
2. Enforce a machine-wide maximum of 10 concurrent ingest workers.
3. Enforce a maximum of 1 concurrent ingest worker per wiki. The main wiki
   counts as one wiki under the same rule.
4. Keep each wiki's activation choice independent: `session_start` or
   `scheduled`.
5. Keep project, main, and both routing unchanged. Scheduling is activation;
   routing remains a separate authority.
6. Work directly on `main` with one writer. Do not create a branch, PR, Goal,
   or automatic review loop unless the user later asks for one.
7. Do not install the new production scheduler or start the real pending queues
   during implementation without a separate explicit user instruction.

## 2. Problem

v0.3.0 creates one macOS LaunchAgent per wiki root. The label and plist path
are derived from the canonical wiki path, and every plist embeds the absolute
path of the installed plugin snapshot.

That design is safe and simple for one wiki, but it creates unnecessary
operator work as the number of project wikis grows:

- every wiki needs a separate scheduler installation;
- every plugin reinstall requires every scheduled wiki to be uninstalled and
  installed again;
- machine-wide provider consumption has no single hard ceiling;
- status and lifecycle checks are fragmented across multiple plist files;
- a new trusted wiki does not automatically join scheduled processing.

The existing trusted runtime layout already provides a machine-local registry:

```text
${XDG_CONFIG_HOME:-~/.config}/karpathy-wiki/
  wikis/<wiki-hash>/runtime.toml
  workspaces/<workspace-hash>/runtime.toml
```

Only the `wikis/*/runtime.toml` records are scheduler inputs. Workspace routing
records must never be treated as ingest registrations.

## 3. Outcome

One short-lived machine coordinator wakes on a fixed base interval, enumerates
explicitly trusted wiki runtime records, selects due wikis whose
`dispatch_mode` is `scheduled`, fills at most 10 machine slots and at most one
slot per wiki, then exits.

It is not a resident model process and it does not scan the filesystem looking
for arbitrary `.wiki-config` files.

```text
one LaunchAgent
    -> load private scheduler config
    -> enumerate private wikis/*/runtime.toml
    -> validate trust and canonical wiki roots
    -> filter dispatch_mode=scheduled and due interval
    -> deduplicate by canonical wiki_root
    -> acquire global slots, maximum 10
    -> acquire at most one per-wiki slot
    -> run existing scheduled scan/tick
    -> persist bounded scheduling state
    -> exit
```

## 4. Configuration authorities

### 4.1 Machine scheduler runtime

Add one private file:

```text
${XDG_CONFIG_HOME:-~/.config}/karpathy-wiki/scheduler/runtime.toml
```

Proposed shape:

```toml
[scheduler]
interval_seconds = 60
max_total_processes = 10
max_processes_per_wiki = 1
```

Requirements:

- parent directories mode `0700`;
- file mode `0600`;
- user-owned and never symlinked;
- atomically written and semantically validated before replacement;
- `max_total_processes` must be an integer from 1 through 100;
- `max_processes_per_wiki` is fixed to 1 in v0.3.1;
- no provider credentials or wiki paths are copied into this file.

### 4.2 Per-wiki runtime

Existing trusted `wikis/<hash>/runtime.toml` remains authoritative for:

- canonical `wiki_root` and trusted workspace;
- `dispatch_mode = session_start|scheduled`;
- provider, model, effort, retries, cooldown, auto-commit;
- the wiki's scheduling interval eligibility.

The coordinator must enumerate these records, then call the existing strict
runtime validator. A malformed, moved, missing, untrusted, symlinked, or
wrong-owner record is reported and skipped without blocking other wikis.

### 4.3 Workspace routing

`workspaces/<hash>/runtime.toml` continues to own only `project|main|both` and
exact routing targets. The global scheduler must not enumerate workspace
routing records. In `both`, the project and main wiki are two independent wiki
runtimes and each consumes at most one machine slot.

## 5. Global concurrency contract

The machine limit must apply to every worker launch source, not only scheduled
ticks. Otherwise `wiki capture`, `wiki ingest-now`, SessionStart, manual ticks,
promotion, or `worker_completion` could exceed 10.

All launch paths must therefore use one shared global slot pool:

```text
${XDG_CONFIG_HOME:-~/.config}/karpathy-wiki/scheduler/slots/
```

Each global lease records at least:

- global slot number;
- canonical wiki root or stable wiki hash;
- per-wiki run ID and lease path;
- wrapper PID and provider PID;
- profile and provider;
- creation and heartbeat timestamps.

Rules:

1. Acquire the global dispatch lock before allocating a global slot.
2. Never allocate more than 10 valid global leases.
3. Never allocate a second lease for the same wiki in v0.3.1.
4. Claim the per-wiki capture and lease as one bounded transaction. On any
   partial failure, restore the capture and release both leases.
5. Every terminal, retry, interruption, auth failure, rate limit, and spawn
   failure path releases or deliberately retains both lease layers together.
6. Reconcile only leases whose wrapper and provider are both dead. Never
   duplicate a live provider because a heartbeat is old.
7. Global lease filenames and contents are mode `0600` under a `0700` parent.

The existing per-wiki dispatch lock remains. Use one documented acquisition
order everywhere to prevent deadlocks. Preferred order:

```text
global dispatch lock -> per-wiki dispatch lock -> global lease -> per-wiki lease
```

No code path may acquire those locks in the reverse order.

## 6. Fairness and refill

A machine cap alone is insufficient. With 11 non-empty wikis and 10 slots, a
busy wiki must not continuously reclaim the released slot while the eleventh
wiki starves.

Required behavior:

- a coordinator sweep offers at most one worker per eligible wiki;
- eligible wikis are selected round-robin, with stable canonical path as the
  deterministic tie-breaker;
- persist only the minimal cursor or last-served state needed for fairness;
- when a worker completes and a global scheduler is installed, refill through
  the global coordinator instead of refilling only the same wiki;
- when no global scheduler is installed, preserve the v0.3.0 local refill
  behavior while still honoring the global slot limit if the machine scheduler
  configuration exists;
- capture and manual ticks may request a refill but may not bypass the queue,
  per-wiki limit, or machine limit.

Per-wiki `schedule_interval_seconds` remains an eligibility cadence. The
machine LaunchAgent may wake every 60 seconds, while the coordinator skips a
wiki until its own interval is due. A newly enabled wiki is due immediately.

## 7. CLI contract

Target v0.3.1 surface:

```text
wiki scheduler install                 install or refresh the one machine scheduler
wiki scheduler uninstall               remove the machine scheduler
wiki scheduler enable <wiki>           set one trusted wiki to scheduled
wiki scheduler disable <wiki>          set one trusted wiki to session_start
wiki scheduler status                  machine summary plus registered wiki states
wiki scheduler status <wiki>           one wiki's effective state
wiki scheduler tick-all                one bounded coordinator pass
```

Compatibility for v0.3.0 commands:

- `wiki scheduler install <wiki>` acts as `install` followed by
  `enable <wiki>` and prints one migration notice;
- `wiki scheduler uninstall <wiki>` disables only that wiki and leaves the
  global scheduler installed;
- removing the global scheduler while scheduled wikis remain enabled must
  either fail with an actionable message or require an explicit force flag;
- `status` must report `mismatch` when a wiki says `scheduled` but the global
  LaunchAgent is absent or unhealthy.

The global LaunchAgent label is constant for the user account, for example:

```text
com.toolboxmd.karpathy-wiki.scheduler
```

It stores one absolute plugin Runtime CLI path. Plugin reinstall documentation
must refresh this one scheduler, not every wiki.

## 8. Failure isolation and observability

One broken wiki must not stop the sweep.

`wiki scheduler status` must show:

- global plist path, loaded state, configured interval, and plugin CLI path;
- active global slots as `n / 10`;
- registered trusted wiki count;
- scheduled, session-start, invalid, missing, cooling, active, and pending wiki
  counts;
- one concise row per invalid or mismatched wiki with an actionable fix;
- per-wiki pending count, active slot, provider profile, last run, and next due;
- duplicate canonical roots collapsed to one scheduler target;
- malformed scheduler state lines counted rather than crashing status.

Logging remains per wiki for ingest details. The coordinator gets one bounded
machine log containing only sweep and lifecycle diagnostics, never capture
bodies, credentials, or full provider output.

## 9. Security boundary

The global scheduler must enumerate only trusted private runtime records. It
must not search repositories, home directories, `.wiki-pointer`, or workspace
routing files for implicit targets.

The accepted v0.3.0 detached-worker P1 remains open. This release must not claim
that global scheduling makes `--always-approve` safe for untrusted input.

Because a global coordinator can reach every trusted wiki, v0.3.1 must at
minimum:

- launch coordinator children with a minimal explicit environment;
- preserve the existing executable-outside-checkout validation;
- keep provider credentials out of logs and scheduler state;
- validate ownership, permissions, symlink status, wiki role, and canonical
  trust before every scheduled tick;
- prevent one malformed runtime from changing or injecting arguments for any
  other wiki.

Full provider sandboxing and deterministic privileged helpers remain the
separate P1 workstream already recorded in `TODO.md`.

## 10. Migration from per-wiki LaunchAgents

The migration must be explicit, idempotent, and rollback-safe:

1. Discover legacy per-wiki plist files with the v0.3.0 label prefix.
2. Validate every corresponding trusted wiki runtime.
3. Prepare and validate the global scheduler config and plist.
4. Stop legacy agents without deleting their plist bytes yet.
5. Install and validate the global agent without starting provider work in the
   migration test path.
6. Preserve each valid wiki's existing activation choice.
7. Remove legacy plist files only after global activation succeeds.
8. On failure, restore and reload every previously active legacy plist and
   leave per-wiki runtime modes unchanged.
9. Report stale legacy plist files whose wiki no longer exists; never silently
   delete them outside an explicitly approved cleanup command.

Our current machine has no per-wiki scheduler installed, so local rollout is a
clean global install. The compatibility and rollback behavior still needs
fixture coverage for other installations.

## 11. Implementation map

Expected production files:

- `scripts/wiki_scheduler.py`: replace per-wiki LaunchAgent ownership with
  machine coordinator install, enable, disable, status, tick-all, and legacy
  migration.
- `scripts/wiki_dispatch.py`: enforce global leases and route completion refill
  through the coordinator.
- `scripts/wiki_config.py`: validate and atomically manage private scheduler
  config; enumerate trusted wiki runtimes without weakening per-wiki trust.
- `bin/wiki`: expose the v0.3.1 scheduler CLI and compatibility aliases.
- `scripts/wiki-status.sh`: show effective global capacity and per-wiki
  activation health without making the global scheduler a routing authority.
- `hooks/session-start`: preserve loader behavior and ensure scheduled wikis are
  loader-only. Change only if a failing RED test proves it is necessary.
- `README.md`, `MANUAL.md`, `TODO.md`: document one-time installation,
  per-wiki enablement, upgrade lifecycle, limits, security boundary, and
  migration.
- `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`, and local
  marketplace metadata: bump together to `0.3.1` only after behavior is green.

Prefer extending existing Python modules. If a new production script is
needed, its unit test must exist and fail before the script is created.

## 12. Test-first work packages

### Package A: registry and global configuration

RED tests first:

- scheduler config is private, atomic, strict, and idempotent;
- enumerate only `wikis/*/runtime.toml`;
- ignore workspace routing records;
- reject symlink, wrong-owner, wrong-mode, malformed, moved, and trust-mismatch
  records independently;
- deduplicate equivalent canonical wiki roots;
- preserve per-wiki activation mode and interval.

### Package B: global slot enforcement

RED fixture with at least 12 trusted wikis:

- never exceed 10 total live workers;
- never exceed 1 worker for any wiki, including main;
- `session_start`, `scheduled`, `capture`, `manual`, promotion, and
  `worker_completion` cannot bypass either limit;
- concurrent coordinator invocations do not duplicate capture claims;
- partial lease creation and spawn failure roll back both lease layers;
- dead leases recover once; live providers are preserved.

### Package C: fairness and refill

RED tests:

- with 11 non-empty wikis, the eleventh receives the next released slot;
- a wiki with a deep queue cannot monopolize repeated refill;
- deterministic results under concurrent completion;
- cooling, rate-limited, malformed, and empty wikis do not block healthy ones;
- per-wiki interval eligibility is respected;
- promotion from project to main does not create a second worker for either
  wiki.

### Package D: global LaunchAgent and CLI

RED tests:

- exactly one constant-label plist is generated;
- plist runs `scheduler tick-all`, has `RunAtLoad`, uses the private config
  home, and points at the installed Runtime CLI;
- install and reinstall are idempotent;
- enable and disable alter only the selected wiki runtime;
- uninstall refuses or clearly handles enabled scheduled wikis;
- status detects absent, loaded, stale-path, and mismatched states;
- one broken wiki does not fail the global status or sweep.

### Package E: legacy migration and packaging

RED tests:

- multiple legacy plists migrate to one global plist;
- failure restores every old plist byte-for-byte and reloads prior agents;
- stale legacy targets are reported, not silently deleted;
- plugin reinstall documentation refreshes one global scheduler;
- installed-cache packaging tests use the v0.3.1 Runtime CLI path;
- both plugin manifests and marketplace version agree on `0.3.1`.

## 13. Verification ladder

Use risk-based validation during development:

1. Run the smallest owning test after every focused change.
2. Run scheduler, dispatcher, config, provider-worker, routing, and packaging
   groups after each completed work package.
3. Run `git diff --check` before every commit.
4. Run the full suite once on the final exact HEAD.
5. Run a disposable macOS LaunchAgent lifecycle canary. It must leave no label,
   plist, worker, processing file, or global lease behind.
6. Run a disposable 12-wiki concurrency acceptance proving maximum 10 total,
   maximum 1 per wiki, and eventual service for the eleventh wiki.
7. Do not use the real 55-item project queue or 4-item main queue as the test
   fixture.

## 14. Commit plan on main

One writer, small reversible commits:

1. `test: specify machine-wide scheduler registry and limits`
2. `feat: enforce global ingest slot pool`
3. `feat: add machine-wide scheduler coordinator`
4. `test: cover global scheduler lifecycle and migration`
5. `docs: document one-scheduler activation model`
6. `release: bump karpathy-wiki to 0.3.1`

Do not create RED-only commits that leave `main` unusable. The test may be
written first locally, but commit the test with its smallest GREEN behavior if
the repository must remain releasable after every direct-main commit.

## 15. Done when

v0.3.1 is complete only when all are true:

1. One and only one machine LaunchAgent owns scheduled activation.
2. A newly trusted wiki joins scheduling by selecting `scheduled`, without a
   new plist.
3. Twelve-wiki acceptance proves no more than 10 simultaneous workers.
4. The same acceptance proves no more than 1 simultaneous worker per wiki.
5. Every worker launch source honors both limits.
6. The eleventh eligible wiki eventually receives a released slot.
7. One invalid wiki cannot block healthy wiki processing.
8. Legacy per-wiki scheduler migration is idempotent and rollback-safe.
9. `session_start` remains functional for wikis not enabled for scheduling.
10. Project, main, and both routing behavior is unchanged.
11. Global and per-wiki status output is actionable and deterministic.
12. The global scheduler remains short-lived and leaves no resident model when
    queues are empty.
13. Focused controls, disposable macOS canary, 12-wiki acceptance, full suite,
    plugin packaging validation, and `git diff --check` all pass on exact HEAD.
14. Plugin manifests and marketplace report version `0.3.1`.
15. No real scheduler is installed and no production queue is started until the
    user explicitly approves rollout after implementation.
